# Version 1 — the socket

*Companion notes for [`src/main.rs`](../src/main.rs) as of the `v1` tag. There is no V0 to
compare against: everything here is new. Tests: `cargo test` — 4 unit, 5 end-to-end.*

## What V1 is, in one paragraph

A program that binds `127.0.0.1:7878`, accepts a connection, reads **once** into a fixed
1024-byte buffer, prints what arrived, writes 44 bytes back, and closes. One connection at
a time, on purpose. No HTTP, no threads, no dependencies. The interesting part is not the
program: it is what the socket does to your assumptions on the way through.

## The diagram

One picture for the whole document, and for every version after it. Notation:

- a numbered row is one step, with the function that runs it in `[brackets]`
- `├─` is a decision; every branch says which condition takes it
- `⇢` marks the boundary to the kernel (a syscall)
- every arrow carries a value **and its Rust type**
- `stdout:` / `stderr:` name the stream the text appears on; `exit N` ends the process;
  `↺` means back to the accept loop, with the process still alive

### ⑨ Inside one connection: read once, print, answer, close

```text
 a  buffer = [0u8; 1024]                        [u8; 1024] on the stack, zeroed
    ▼
 b  stream.read(&mut buffer)                   ⇢ syscall, ONE call, may block
    ├─ Err(e) ───────────────────────────────► return Err(e) ──► ⑧ Err arm
    ▼  Ok(bytes_read)                            usize
 c  received = &buffer[..bytes_read]             &[u8] with length = bytes_read
    ├─ bytes_read == 0   "end of input: the peer closed, no bytes arrived"
    │     └─► log: "rustserver: 0 bytes from {peer} (closed before sending anything)"
    │         return Ok(0)                      ← no reply is written
    ▼  bytes_read > 0
 d  log: "rustserver: {bytes_read} bytes from {peer}"
 e  for line in String::from_utf8_lossy(received).lines()
    │      &[u8] → Cow<str> (borrowed if valid UTF-8, U+FFFD otherwise) → &str
    └─► log: "rustserver: | {line}"
    ▼
 f  stream.write_all(RESPONSE)                 ⇢ syscall loop until 44 bytes taken
    ├─ Err(e) ───────────────────────────────► return Err(e) ──► ⑧ Err arm
    ▼  Ok
 g  log: "rustserver: sent 44 bytes, closing"
 h  return Ok(bytes_read) ────────────────────► ⑧ Ok arm
 i  `stream` dropped → close(fd) → FIN, or RST if bytes are still unread
```

Every `?` in ⑨ is a way to leave early with `Err(e)`: `read` in (b), the three `writeln!`s
in (c)(d)(g) writing the log, and `write_all` in (f). All of them drop `stream`, so ⑨ has
no path that leaks a connection, and no path that reports success for a failed exchange.

### Every way out of ⑨, and what the client gets

| step | condition | printed where | client sees | process |
| --- | --- | --- | --- | --- |
| b | `read` fails: reset, or a timeout | stderr: `rustserver: {peer}: {e}` | reset, or no answer | alive, back to ⑥ |
| c | `bytes_read == 0`: the peer closed first | stdout: `rustserver: 0 bytes from {peer} (closed before sending anything)` | nothing — it had already closed | alive, back to ⑥ |
| e | the bytes are not valid UTF-8 | stdout, with U+FFFD standing in for each bad byte | — | alive, carries on to (f) |
| f | `write_all` fails: the peer is gone | stderr: `rustserver: {peer}: {e}` | nothing, or a reset | alive, back to ⑥ |
| h | worked, nothing left unread | stdout: byte count, one line per line, `sent 44 bytes, closing` | 44 bytes, then end of stream | alive, back to ⑥ |
| h | worked, but bytes are still unread | the same three kinds of log line | 44 bytes and/or a reset, depending on timing | alive, back to ⑥ |

### Wrong turns, and where the data actually goes

| wrong turn | what happens to the bytes | where to check it |
| --- | --- | --- |
| 3000 bytes sent at once | `read` takes 1024; 1976 stay in the kernel's receive buffer; `close` then sends RST, not FIN | "More than a bufferful", below |
| one request sent as two writes | the first `read` returns only the first piece; V1 never calls `read` again, so the rest dies with the socket | no test: V1 cannot tell the difference. This row is why V2 has a read loop |
| a client that connects and says nothing | `read` returns 0 → reported as end of input, no reply written | `a_client_that_sends_nothing_is_end_of_input_not_an_empty_message` |
| a client that vanishes mid-exchange | `write_all` returns `Err` → stderr, loop carries on | `a_connection_that_cannot_be_answered_is_reported_not_swallowed` |
| two clients at the same time | the second waits in the kernel's listen backlog until the first is finished (4 s, measured below) | "One connection at a time, felt rather than described" |
| the port is already taken | fails at ② before any connection exists | end-to-end `a_port_already_in_use_is_reported_and_exits_one` |
| a wrong command line | fails at ① before the socket exists | end-to-end `a_wrong_command_line_exits_two` |


| requirement | where | tested by |
| --- | --- | --- |
| starts and prints its listening address | `run`, line 94 — `local_addr()` and `println!` | `tests/server.rs::the_server_reads_prints_answers_and_closes` |
| accepts a TCP connection | `serve`, line 127 — `for incoming in listener.incoming()` | the same test, via a real `TcpStream` |
| reads the data and prints it | `handle_connection`, line 158 — the `read`, then one printed line per line received | `src/main.rs::the_server_reads_what_the_client_sends_and_answers_it` |
| sends a response back | same function, `stream.write_all(RESPONSE)` | both |
| closes the connection | *not a line of code* — see below | the client's `read_to_end` returning at all |
| a failure is not silently swallowed | `if let Err(source) = handle_connection(...)` | `a_connection_that_cannot_be_answered_is_reported_not_swallowed` |

That missing fifth line is the first Rust lesson of this version. There is no `close()`
call anywhere, because `handle_connection` takes the `TcpStream` **by value** and dropping
the last owner of a socket closes it. Every early return — including the `?` on a failed
read — is a close, and there is no path through the function that leaks a connection. In
Python you would write `conn.close()`, and you would be responsible for it running.

## What happens on the wire

```text
TcpListener::bind("127.0.0.1:7878")   ──► the kernel owns a port and a listen queue
   │  .incoming()                  one io::Result<TcpStream> per connection
   ▼
TcpStream                    the accepted socket: a file descriptor with a
   │                         receive buffer on this side and one on the peer's
   │  .read(&mut buffer)      "hand me what has ARRIVED, up to 1024 bytes"
   ▼
usize (bytes_read)           ← the type that makes the whole question
   │  &buffer[..bytes_read]    the only bytes that are data
   ▼
&[u8]                        a slice with the length baked into the type
   │  String::from_utf8_lossy
   ▼
Cow<str>                     borrowed if the bytes were valid UTF-8
   │  .lines()
   ▼
stdout                       one line per line, `| ` gutter
   │
   │  stream.write_all(RESPONSE)   the reply, before the close that follows
   ▼
drop(stream)                 ◄── the close. FIN, or RST if bytes are still unread
```

## The question: why does `read` return a number of bytes?

Because TCP is a **stream of bytes**, and the kernel does not know where your messages
begin and end. It has a receive buffer, packets land in it, and `read` means "give me what
is in there now". The number is the answer to the only question that matters: *how much of
what I asked for was actually there?*

Three things follow from that number, and all three are visible in V1's own output:

1. **A short read is normal, not an error.** Send 3000 bytes and the server reads 1024:

   ```console
   rustserver: 1024 bytes from 127.0.0.1:65340
   rustserver: | xxxxxxxx…
   rustserver: sent 44 bytes, closing
   ```

   The other 1976 bytes were still in the kernel, waiting for a second `read` that this
   version never makes. Nothing was lost; nothing was read either.

2. **Two messages can arrive as one read, and one message as two.** The browser's request
   and your `nc` line are the same thing to the socket. If a request is split across two
   packets, you get it in two calls — there is no length prefix and no delimiter in TCP
   itself. The application has to define one. For HTTP, that delimiter is `\r\n\r\n`, and
   finding it is V2's first job.

3. **0 means "no more bytes will ever arrive", not "an empty message".** `read` returning
   `Ok(0)` is the socket's way of saying the peer closed. That is why the handler has a
   branch for it:

   ```console
   rustserver: 0 bytes from 127.0.0.1:65350 (closed before sending anything)
   ```

The count is also what makes the buffer safe. `[0u8; 1024]` is always 1024 bytes long, so
without the count you cannot tell the request from the zeroes around it: printing
`buffer` instead of `&buffer[..bytes_read]` would send 1024 bytes to every client with
1018 zeroes on the end, and a browser would hang instead of parsing. Rust makes the
distinction a type — `&[u8]` with a length — rather than a convention you remember.

That leaves the question V1 does not answer: **if a message has no end in the stream, when
do you stop reading?** HTTP says: stop at the blank line, and if the client never sends
one, you still have to answer or time out. Nothing in `std::io::Read` will decide that for
you.

## What the compiler insisted on

None of these are preferences. Each one is a type error you can reproduce by deleting the
piece and rebuilding.

| insisted on | why | what happens without it |
| --- | --- | --- |
| `mut stream` in `handle_connection` | `read` and `write_all` take `&mut self` | `E0596: cannot borrow as mutable` — and the fix is *where* you put the `mut` (on the binding, not the type) |
| `[0u8; READ_BUFFER]`, not `Vec::new()` | the buffer has to exist before anything can be read into it | the compiler cannot know the length, so `read` has nothing to fill |
| `&buffer[..bytes_read]` | `from_utf8_lossy` wants `&[u8]`, and only part of the array is data | passing `&buffer` compiles and sends 1024 bytes, zeroes included |
| the stream passed **by value** | ownership is what makes "closed at the end" true on every path | `&TcpStream` would leave the close to the caller's discipline |
| `log: &mut impl Write` | the handler should not know it is talking to a terminal | hard-coded `println!` cannot be asserted on; the test would have to parse stdout |
| `peer` passed in, not read inside | `peer_addr()` can fail, and what to do about that is the *loop's* policy, not the handler's | the handler would need an error variant or a made-up fallback address |

One more decision is worth naming because it looks like a style choice and is not: the
severity split in `Error`. "This socket cannot be created" is fatal — exit 1. "This
connection broke mid-exchange" is not fatal at all: it is printed, and the loop accepts the
next client. "You typed the command line wrong" is neither — exit 2, plus the usage text,
the same convention `eventlog` uses. A server that dies because one client disconnected
early is not a server.

## The failure the tests found: closing on unread bytes sends RST

The first version of `a_request_larger_than_the_buffer_arrives_one_bufferful_at_a_time`
sent 2048 bytes and cheerfully did:

```rust
client.read_to_end(&mut response).expect("read the response");
```

It failed, and the reason is the most useful thing this version produced:

```text
read the response: Os { code: 54, kind: ConnectionReset, message: "Connection reset by peer" }
```

The server read 1024 bytes, answered, and closed — with 1024 bytes still sitting unread in
its receive buffer. POSIX is explicit about what `close()` does then: it sends **RST**, not
FIN, and an RST tells the peer to throw away whatever is still queued for it. The reply was
written, and the reset wiped it out before `read_to_end` finished.

So the test now asserts the reset on purpose:

```rust
// The other 1024 bytes are still in the kernel's receive buffer, and closing a
// socket while bytes are unread makes the kernel send RST rather than a polite FIN.
...
assert!(reply.is_err(), "closing on unread bytes resets the connection, got {reply:?}");
```

That is the shape of most "my server works in `nc` but the browser says reset" bug reports,
and it is why V2 cannot answer until it has read the whole request: the request has to be
consumed (`\r\n\r\n`), or the response has to be followed by a polite half-close and a
drain. Note the test asserts `is_err()` rather than a specific errno: the reset is the
guaranteed part, the exact code is the platform's business.

The end-to-end tests are the ones worth reading if you only read one: they start the real

other and with a server you have open yourself.

## Run these yourself

Everything below is a real transcript from this machine, not an illustration.

```console
$ cargo run
rustserver: listening on 127.0.0.1:7878
rustserver: try `printf 'hello\n' | nc 127.0.0.1:7878`
```

In another terminal, the acceptance test from the brief:

```console
$ printf 'hello from netcat\n' | nc -w 2 127.0.0.1 7878
rustserver v1: read your bytes, closing now
```

and the server's side of it:

```console
rustserver: 18 bytes from 127.0.0.1:65338
rustserver: | hello from netcat
rustserver: sent 44 bytes, closing
```

A browser is a much more demanding client. `curl -v` shows both halves at once — what it
sends, with the `\r\n` that `nc` hides, and what it makes of the reply:

```console
$ curl -v http://127.0.0.1:7878/
> GET / HTTP/1.1
> Host: 127.0.0.1:7878
> User-Agent: curl/8.7.1
> Accept: */*
>
* Received HTTP/0.9 when not allowed
curl: (1) Received HTTP/0.9 when not allowed
```

That is V2's specification, handed over by a real client: *answer in HTTP, or be rejected.*
The server read the whole request and printed it, including the blank line:

```console
rustserver: 77 bytes from 127.0.0.1:65339
rustserver: | GET / HTTP/1.1
rustserver: | Host: 127.0.0.1:7878
rustserver: | User-Agent: curl/8.7.1
rustserver: | Accept: */*
rustserver: | 
rustserver: sent 44 bytes, closing
```

Now the interesting ones.

**More than a bufferful.** `head -c 3000 /dev/zero | tr '\0' 'x' | nc -w 2 127.0.0.1 7878`
— 3000 bytes in, 1024 read:

```console
rustserver: 1024 bytes from 127.0.0.1:65340
```

**A client that says nothing.** `nc -w 1 127.0.0.1 7878 < /dev/null` — no data, so no
reply, and the server says which it was:

```console
rustserver: 0 bytes from 127.0.0.1:65350 (closed before sending anything)
```

**One connection at a time, felt rather than described.** Hold a connection open without
sending anything (`sleep 5 | nc -w 10 127.0.0.1 7878`) and then time a second client:

```console
$ printf 'second client\n' | nc -w 10 127.0.0.1 7878
rustserver v1: read your bytes, closing now
the second client waited 4s
```

Four seconds of doing nothing, because the server was blocked in `read` on the first
client. That is head-of-line blocking, and it is not a bug in this version — it is the
constraint V1 accepted. (The second client's `connect()` succeeded immediately: the kernel
queues it in the listen backlog. It is the *answer* that waited.)

cargo test --test server        # only the end-to-end ones
cargo test -- --nocapture       # show the server's own stdout while they run

## Experiments before V2

Each one answers a question V2 is about to ask. Do them in this order.

1. **Make the boundary problem unavoidable.** Send 3000 bytes as above, then raise
   `READ_BUFFER` to 4096 and send 5000. The failure does not go away, it moves. What does
   that say about choosing a buffer size as a strategy?
2. **See the `\r\n`.** Change one line to
   `writeln!(log, "rustserver: | {:?}", String::from_utf8_lossy(received).escape_debug())`
   and send a `curl` request. `\r\n` becomes visible as text, including the final `\r\n\r\n`
   — the delimiter V2 has to find. Put it back when you are done.
3. **Watch a message become two reads.** Set `READ_BUFFER` to 8 and load a browser request.
   The server reads 8 bytes of a 77-byte request and prints fragments of `HTTP/1.1`. Then
   ask: with a buffer this small, how many `read`s until you have the blank line, and what
   stops you reading forever if it never comes?
4. **Break the fifth requirement on purpose.** Delete the `bytes_read == 0` early return so
   the server always writes a reply. A silent client now gets a reply nobody can read, and
   the write fails. Watch what the server prints: an error, on stderr, for that connection
   only — the process stays up and the next client is served. That is the difference between
   a reported failure and a swallowed one.
5. **Send something that is not text.** `head -c 40 /dev/urandom | nc -w 2 127.0.0.1 7878`.
   The server keeps running and prints replacement characters, because `from_utf8_lossy`
   cannot fail by design. Which conversion would you rather have on a network path:
   `from_utf8` with an error branch, or this?
6. **Nothing about performance yet.** V1 serves one connection at a time; no
   micro-optimisation survives the client that blocks for five seconds. Profile later.

## What V2 will ask of this code

V1 was written with V2 in mind in five places. Confirm them before we move on.

1. `handle_connection` returns `usize`, the count of bytes read. V2 returns a **parsed
   request** instead: same function, different answer. Keeping the number in V1 is what
   makes the upgrade visible in a diff.
2. `log: &mut impl Write`, not `println!`. V2's tests can then assert on parsed requests and
   rendered responses without capturing a terminal.
3. `READ_BUFFER` exists as a name, and the single `read` is one line. V2 turns it into a loop
   that reads until `\r\n\r\n`, and moves `bytes_read == 0` from "a case to print" to "a case
   to stop on".
4. `RESPONSE` is a `const &[u8]` sent with one `write_all`. V2 renders a status line, headers
   and a `Content-Length` from the request it parsed — which is where a response stops being
   a constant.
5. `serve` knows nothing about protocols. The accept loop, the per-connection error policy,
   the greeting and all five end-to-end tests should survive V2 without a single change. If
   they do not, V2 changed an interface rather than adding a protocol — worth noticing at the
   time rather than afterwards.

The open questions V2 forces, none of which are answerable yet:

- Where does a request *end*, and what happens if the client never sends the end?
- Whose job is it to bound the read — the handler, the loop, or a parameter?
- If the request line is `GET /index.html HTTP/1.1`, is the path a `String`, a `&str`
  borrowed from the buffer, or an enum of things the server knows how to answer?
- And the one this version leaves open on purpose: what should a server *do* with a client
  that is waiting for the answer to a request it has not finished sending?
